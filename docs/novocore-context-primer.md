## What NovoCore is

An internally-owned system for Novotrade S.A. (Java Jives) replacing Manager.io, and eventually Prosvasis Go. **Not just "replace Manager"** — the real goal is unifying data across disconnected systems, automating repetitive tasks, and generating real reports. Manager replacement is the first workload, not the purpose. No regulatory/compliance filing responsibility sits with NovoCore — the external accountant handles that; Go remains the invoicing system of record until Phase 11.

## Resolved technical decisions (ADRs in `docs/decisions/`)

- **0001** Java 25 LTS + Maven. Java 25 forces the **Spring Boot 4.x** line (3.5 does not support it), which brings JUnit 6, Testcontainers 2.x and Flyway 12. Accepted knowingly.
- **0002** ArchUnit used as a plain library, not via `archunit-junit5` — no `archunit-junit6` exists and the JUnit 5 variant binds to JUnit Platform 1.x.
- **0003** Multi-module layout so the adapter boundary is a **compile error**, not just a test failure: adapters will depend on `core-api` only, so core entities and repositories are absent from their classpath.
- **0004** **Goods Receipt creates Inventory Lots**, not Purchase Invoice posting, with a **GR/IR clearing account** absorbing the timing gap in either direction. Chosen because brief §6's myDATA-first import means goods routinely arrive before their invoice exists. **Built in step 8**; its one open item is closed by ADR 0008.
- **0005** **EUR-only behaviour, but currency is modelled from day one.** `Money` always carries a currency and every monetary column has one. No rates, no FX gain/loss.
- **Entity ids are `bigint`** (not UUID) — single self-hosted instance, smaller indexes.
- **Money is exactly 2 decimals**, normalised on construction; **unit costs and quantities are 6**. A more precise money value is rejected, never silently rounded. **`UnitCost` is that own type, built in step 6** — `extend()` is the only route back to `Money` and it names its rounding mode, so precision is only ever given up where the code says so. Zero is a valid unit cost (a free sample is a real lot); negative is not.
- **Every monetary column carries a `char(3)` currency companion**, named `<column>_currency`, tied by a biconditional CHECK. Settled by the schema's first monetary column, `product.selling_price` in step 5, and enforced across the whole schema by `SchemaConventionsIT`. A JPA field mapping a `char(3)` needs `@JdbcTypeCode(SqlTypes.CHAR)`. **Since step 6 the rule also covers monetary `numeric(19,6)` columns, discriminated by a `_cost` suffix** — scale alone cannot tell a unit cost from a VAT rate or a quantity, so the name has to.
- **`Quantity.times(Quantity)` is exact and throws rather than rounding.** Two 6-decimal quantities multiply to 12 places, so the naive version fails on its own trailing zeros; a product that genuinely needs more than 6 places is a modelling error, not a rounding question.
- **Attachment content is stored in PostgreSQL** (`bytea`), so backup and restore stay one atomic artefact.
- **0006** **Correction policy (Q13): documents are immutable, our own records are editable.** Invoices and credit notes are corrected by a reversing entry; receipts, payments, transfers and manual entries are edited in place with the previous state written to the audit log. The line drawn is whether the record exists *outside* NovoCore. Enforced in the database, and the policy is stated once as an SQL function both triggers call, with a test proving it agrees with the Java enum. **The inventory write-off was added to the immutable list** — flagged as an addition and explicitly approved.
- **0007** **VAT posting (Q14): separate Output VAT and Input VAT, never netted.** Per-line computation summed by rate, which is why a journal line carries its VAT class and taxable base — without them two Output VAT lines at different rates are indistinguishable amounts. Reverse charge needs no new structure; exempt lines post no VAT line at all.
- **0009** **Open item matching is a layer over AR/AP, not a second ledger: documents post, allocations post nothing.** Both ends of an allocation are already in the same control account, so an entry for it would debit and credit that account for the same amount. Consequences: **no document stores an open amount and nothing stores a "paid" flag**, and an allocation can be reduced or released without touching a posted entry — which is what makes **Q13's second half** implementable at all. `release` deletes a row, the one place this schema does, because an allocation is a statement about a current relationship rather than a record of an event. The ADR also carries **Q15's remainder** (confirm at entry, record the confirmation, no queue) and **Q10** (the retail customer is seeded and structural).
- **0008** **Three answers sharing one principle: a posting that reflects a physically verified event does not change once other things depend on it.** (1) *ADR 0004's open item* — a price difference posts to a **purchase price variance** account and the lot keeps the cost it was received at; re-costing a lot FIFO has already consumed into posted COGS is the same problem as editing a posted entry, expressed as a number. (2) *Q17* — a sale may drive **aggregate stock negative**; it is recorded as a shortfall, subtracted from the sellable figure so the product genuinely reads negative, queryable for review, and never retro-costed. (3) *Q39* — a **Goods Receipt is immutable**, corrected by a reversal that un-receives the lots and posts the mirror together, and refuses once they have been touched. **Constrains Q18** for step 10: allocate against the received cost, never reach back into consumption already costed out.

## Architecture (non-negotiable)

- **The core owns its data model** — never shaped by an external system's schema (Go, WooCommerce, etc.).
- **Ports and adapters**: adapters translate external systems into the core's model; a black-box swap only touches its adapter. Internally-driven functionality is a **module** instead.
- **Field boundary rule**: a field belongs in the core only if the core's ledger/reports/modules genuinely need it. External system reference IDs (Go ID, Woo ID) never live on core entities — each adapter keeps its own mapping table.
- **Governance**: adapters/modules call the core only through defined interfaces (enforced by ArchUnit); contract tests per adapter; fail-loud, never silently guess.
- **Performance**: core operations complete instantly, never synchronously wait on an external adapter call.
- **Never silently resolve ambiguity** — this shows up everywhere: rounding, customer matching, bank matching, invoice categorization. Auto-resolve only what's certain; suggest and require confirmation otherwise.
- **Code-quality governance beyond structural boundaries**: automated tests for core logic, prefer root-cause fixes over patches, periodic cleanup passes — architecture alone doesn't prevent patch-accumulation spaghetti.

## Tech stack

**Backend:** Java + Spring Boot, PostgreSQL, Docker, self-hosted (HTTPS reverse proxy from day one). Ruled out: SQLite, Python/PHP backend, cloud hosting for v1, bank payment initiation, cloning a vendor's feature set.

**Frontend:** Vite + React + TypeScript + Tailwind + shadcn/ui, in `/frontend/`, separate from backend. Default shadcn theme until Claude Design sets the real brand look. Ask (don't guess) when a UI element could reasonably use more than one shadcn component.

**Shared core services:** Email sending (SMTP via Settings, one interface, called by any feature — never per-module SMTP config). Document attachments, same principle.

## Domain model summary

**Chart of accounts — built and committed (step 3).** The full account list, decisions and
per-step obligations are in `docs/PROGRESS.md`. Resolved shape:

- **Two levels only:** an `AccountGroup` entity (name + `displayOrder`) with accounts under it. Not a self-referencing Account tree. Groups are an entity rather than flat text because ordering is **manual/drag-and-drop**, which needs somewhere to store a group's position. Alphabetical ordering applies only to sub-ledgers (customers, suppliers); inventory sorts by SKU.
- **Normal balance side is derived from account type, never stored** — there is no `normal_balance_side` column and a test asserts its absence. **Seven types**, because both contra types are genuinely needed: `CONTRA_ASSET` (accumulated depreciation is Asset-classified with a *credit* normal balance; without it fixed assets report at roughly double carrying value) and `CONTRA_INCOME` (sales returns are Income-classified with a *debit* normal balance; typed as `EXPENSE` they would sit below the revenue line and overstate gross revenue).
- **Kinds:** Standard / Bank-Cash / Partner Clearing / Control (with a declared sub-ledger type). `type` and `kind` are independent dimensions — accumulated depreciation is `CONTRA_ASSET` *and* `CONTROL`. Control accounts: Accounts Receivable→Customer, Accounts Payable→Supplier, Inventory→Product-Lot, Fixed Assets→Asset, and **GR/IR clearing→Supplier**. A biconditional CHECK enforces "Control iff sub-ledger" in the database, not just in Java.
- **Bank-Cash:** Cash, Alpha Bank, Piraeus Bank, NBG. **Partner Clearing:** Skroutz, ACS Courier, POS provider, **plus PayPal and Stripe** — the latter two grouped under Cash & Cash Equivalents but treated as clearing accounts, so processor fees post as expense on receipt.
- **Account codes are left blank** and ΕΛΠ mapping is null for now (comes from the accountant later). Because neither is usable as a handle, **`AccountSystemKey`** gives the eleven accounts NovoCore's own posting rules must locate a stable machine identifier. Keyed accounts can be renamed and reordered but never deactivated, and the key is never settable from application code.
- **No account balance is stored anywhere** — a balance is the sum of its journal lines, computed on read from step 7. So step 3 introduced no monetary columns at all.
- **`expectedToClear` flag** rather than a fifth kind, for accounts whose residual balance is a real discrepancy: Freight/Landed Cost — Unallocated, GR/IR clearing, Unclassified — Needs Review.
- **Sales is split by channel:** **Store & Phone**, eCommerce, Skroutz — phone named explicitly rather than left to convention. **Sales returns are contra-revenue, one account per channel**, so credit notes keep return rate visible per channel instead of netting into revenue.
- **New accounts** not mapping from Manager: the three expected-to-clear ones, the three Sales returns, `Rounding differences`, `Inventory write-off / shrinkage`, and `Interest expense` in its own **Finance Costs** group (below EBIT, so EBITDA/EBIT stay meaningful).
- **Inventory write-off sits in the COGS group**, its own account separate from Cost of goods sold — gross margin reflects the loss, sale-driven COGS stays clean. **One account with a reason code**, not three; the reason is `WriteOffReason` (built in step 6), and **carrying it on the write-off transaction is now a step 7 obligation**. Distinct from the Damaged Goods *Location*, which marks stock unsellable but still an asset: **moving a lot there posts nothing**, so **phase 8 Clearing Checks must surface lots aging in it** — the agreed compensating control, whose query step 6 built.
- **No delete, only deactivate**; with no period locking no account is ever safely finished with. A reorder must name every member exactly once rather than leaving the rest in an order nobody chose.
- **Dropped:** Suspense, Inter Account Transfers (Manager had the latter under Equity — the error the brief corrects), and DDP (superseded by Freight/Landed Cost — Unallocated).
- **Known imperfections accepted:** `Interest received` stays in `Income` above EBITDA, so EBITDA is approximate; no current-portion split on the NBG loan; `VAT payable` was a single account, replaced in V14 by the Output/Input split (Q14); `Amortization` is seeded although nothing can post to it.

**VAT — built (step 3b), real data from Prosvasis Go and AADE.**

- **`VatClass` is a runtime-editable entity, not an enum**, because Greek rates change by statute (the 3% and island-reduced 4% classes exist only because of αρ.31 ν.5057/2023). Fields: code, description, ratePercent, active, nullable self-referencing reducedCounterpart.
- **Nine classes seeded, eight distinct percentages** — `0`/`1030`/`1040`/`1041`/`1060`/`1091`/`1131`/`1170`/`1410`. 4% appears twice: `1040` in its own right, `1041` as the island-reduced counterpart of 6%. **So the code is the identity, never the rate** — there is deliberately no `findByRate`, and a test asserts its absence.
- **Island-reduced mappings seeded as data** (24→17, 13→9, 6→4 as `1041`, 4→3), held on the mainland rate pointing at the reduced one. Enforced one level deep, lower-rated, one-to-one, never self-referencing. **No automatic rate switching by shipping destination** — future scope by explicit decision.
- **Rates are percentages** (`24.000000`, not `0.24`) in `numeric(19,6)`, with a CHECK allowing **exactly 0 or 1–100**. The lower bound is the load-bearing half: a plain 0–100 range does not catch `0.24` written for 24%, which was a real defect until V10. Zero stays valid because the zero-rated class is distinct from an exempt line. **Rates are never editable in place** — a rate change is a new class plus deactivation, because editing would retroactively change what already-issued invoices appear to have charged.
- **Precedence rule, stated as code** in `VatClassPrecedence`: **invoice line beats customer beats product**, returning which level won. **No fallback rate** — it throws rather than assuming 24%, since a silent default produces a plausible invoice at a rate nobody chose and an undercharge is unrecoverable after issue.
- **`VatExemptionReason` is a separate entity, not a 0% rate** — zero-rated charges 0% under a real rate; exempt is outside VAT because a named article of the Κώδικας ΦΠΑ says so, and myDATA reports them differently. **Seeded (V8) with the real 29 rows from Prosvasis Go**, in the recodified article numbering (άρθρο 2 και 3, 5, 17, … 58). Gaps at codes 24 and 28 — absent from *Go's* list, so worth confirming with the accountant before phase 7. `mydataCode` is stored verbatim, and that turned out to be load-bearing: codes 12 and 13 name "Πλοία Ανοικτής Θαλάσσης" in their description and not in their myDATA string, so composing the value would have transmitted those two wrong. **`mydataCode` is nullable**, because the OSS/IOSS reasons (29–31) have no myDATA mapping in Go — NULL means "no mapping exists", and phase 7 must refuse to transmit one rather than compose a substitute.
- **`ChargeType`** — extensible lookup for fees charged *to* the customer as revenue: name, default VAT class, income account, active. The service **refuses a non-`INCOME` account**, which is the point of it existing: wiring a delivery fee to `Transportation costs` to net it off would understate revenue and cost together. **Seeded (V7) with `Delivery` and `COD fee` against dedicated `Delivery income` and `COD fee income` accounts** (Q27) — a residual bucket holding most invoices' fee lines would be the largest income line and useless as a residual. Both default to 24%, and **Q33 is settled and confirmed with the accountant: a fee's VAT rate is independent of the products on the invoice** — a 13% order still carries 24% delivery. It was raised here as a possible defect on the general principle that an ancillary charge follows the main supply's rate, and the accountant confirmed the treatment as built, so this is settled rather than a recommendation that was overruled. Nothing should later be built to derive a fee's rate from the lines around it. Nothing consumes charge types until step 9.
- **`numeric(19,6)` now covers three things** — quantity, unit cost, and *rate*. The distinction that matters is amount (2dp, because that is a cent) vs multiplier (6dp, must not lose precision before the product is rounded once).
- ~~**Still open: Q14**~~ — **closed in step 7** (ADR 0007): separate Output/Input accounts, per-line computation summed by rate, the class and base carried on the posted line. Q28 (dispatch purpose) is answered as a recommendation only, nothing built.

**Core entities — Product, Customer, Supplier and Asset built (step 5).**

- **Product:** own SKU (unique) and EAN (unique when present), `GOODS`/`SERVICE`, a unit of measure **reference** (a runtime-editable lookup since V11, carrying `allowsFractionalQuantity` and a nullable AADE myDATA code), a **required** default VAT class (there is no fallback rate anywhere, so a product without one could not be invoiced), an optional selling price, one optional supplier plus that supplier's own code. **No Go/Woo ids, no stock column, no last-purchase-price column** — both derived from lots (step 6). **A zero price is refused**; null means "not priced yet", because zero produces an invoice line worth nothing without anyone choosing to give the goods away.
- **Q5 answered: one product, one supplier**, a plain nullable foreign key, no many-to-many. **A supplier SKU without a supplier is refused** in code and by a CHECK — that meaningless state was the whole question.
- **Customer / Supplier:** name, single email, single phone (Q8), VAT number (unique when present), `VatStatus`, and for Customer a nullable VAT class override feeding the precedence rule. **Customer names are not unique; VAT numbers are** — two retail customers can genuinely share a name.
- **Q9 answered: `VatStatus` is shared by both parties** — `DOMESTIC`, `INTRA_EU_B2B`, `NON_EU_EXPORT`, `EXEMPT`, `OTHER`. **Five, not four:** export and intra-EU B2B are both VAT-free under *different* articles and are reported differently, so folding export into "other" would lose what has to be stated. Intra-EU requires a VAT number, exempt requires a `VatExemptionReason`; both definitional and both database constraints. **No VIES validation** — that adapter is phase 7.
- **Matching is split by certainty** (rule 7): `findByVatNumber` is exact and may be applied automatically; `suggestMatches` on name/email/phone returns candidates a human confirms. A blank VAT number matches nothing. **Merge is not built** — brief §5's alias-forward needs the ledger, and half of it would be a merge that appears to work and loses references.
- **Asset — a register, not a valuation.** Name, optional code, acquisition date, an optional later depreciation-start date, `IN_USE`/`DISPOSED` with a disposal date required exactly when disposed, and **a manually set annual straight-line rate (Q12)**. **No monetary field at all**: both fixed-asset control accounts declare `ASSET` as their sub-ledger, so cost and accumulated depreciation are sums of journal lines. No useful life (it is `100/rate`), no salvage value (Greek tax depreciates to zero), no method field (straight-line only).
- **The rate is nullable, and that is the current state**: the statutory rates per category are pending the accountant. Null means "not yet known"; nothing was guessed and no category table was created. `withoutDepreciationRate()` lists the assets still waiting. The rate is bounded **1–100** — the lower bound is the load-bearing half, because a plain 0–100 range cannot catch `0.1` written for 10%.
- **Step 4's field restrictions now bite.** `ProductView.redactedFor(RoleView)` is the single implementation, tested against the real seeded Remote/Order Staff role. Hiding the supplier also hides the supplier's SKU, since that code identifies the supplier indirectly. ⚠️ `ProductService` has unredacted reads for the core's own costing rules and `...For(viewer)` variants that redact — **a named convention, not an enforced one**; the first Products controller must be reviewed for it.
- **Product gained two flags in step 6:** `serialTracked` (individually identified stock — brief §5's coffee machines) and `bundle`. Both are refused for a service; a bundle cannot be serial-tracked; neither can be changed once the product has lots. `isStocked()` is now `GOODS && !bundle`, because a bundle is typed GOODS and still holds no stock of its own.

**Inventory — built (step 6). Q7, Q25 and Q11 all answered.**

- **Q7: stock is exposed per location plus a computed sellable figure, and sellable is the Inventory location only** — excluding Damaged Goods and Service. `InventoryService.stockOf` returns `StockLevels`, which carries every location (zero where empty) and derives `sellable()` from `StockLocation.sellableLocations()`, so a second sellable location is one edit rather than a hunt for hardcoded `INVENTORY`. Nothing is stored (brief §5); it is computed on every read. This is why a single stock number was always wrong: nine on hand and three sellable is the ordinary case.
- **`StockLocation` is an enum, not a table** — the opposite call from `VatClass` and `UnitOfMeasure`, because these three values are NovoCore's own and each has behaviour attached: `INVENTORY` is what sellability is computed from and `DAMAGED_GOODS` is what phase 8's Clearing Checks must single out. A runtime-added row would be storable and unhandled. **Not a warehouse** — these are states of stock, not places on a map. Named `StockLocation` because a bare `Location` reads as an address (Q37).
- **A lot has two shapes, and the rule is: location lives wherever the quantity does.** Pooled stock stores its quantities and location on the lot. A **serial-tracked lot stores neither** — the quantity *is* the count of its units, and each unit carries its own location, because three machines received together are one lot and one going out for repair must not move the others. Storing a quantity on a serial-tracked lot would be a second copy of a derivable number, the argument that keeps a cost off `Asset`. One CHECK refuses any third shape. Consequently `moveLot` refuses a serial-tracked lot and `moveUnit` refuses one not on hand.
- **Moving to Damaged Goods still posts nothing** (the step 3 decision), and step 6 built the query the phase 8 compensating control needs: `lotsAt(location)` covers both shapes and excludes exhausted lots.
- **Serial numbers are unique across all stock.** A stronger claim than the world strictly supports, and still right: within one business, a repeated serial is overwhelmingly a duplicate scan, and catching that beats accommodating a collision nobody has seen.
- **Q25: `WriteOffReason` is a fixed enum** — `SHRINKAGE` / `DAMAGE` / `EXPIRY` / `OTHER`. Reportability is the entire reason one write-off account was chosen over three. **⚠️ It has no consumer yet**: a write-off derecognises an asset, so it needs the journal engine, and reducing a lot without the entry would leave the stock gone and the balance sheet carrying it. **Step 7 obligation** — including brief §5's exception that a *serialized* write-off uses the named unit's own actual cost, with no FIFO.
- **`SerializedUnitStatus.SOLD` is declared and unreachable**, deliberately: brief §5 wants the customer/invoice link on a sold unit, and that is step 9. The stock count already reads the status column, so it will be right the day a unit sells.
- **Last purchase price is now populated** from the most recent lot's unit cost, by acquisition date rather than insertion order (Q6). **⚠️ Step 10 obligation:** a lot's unit cost includes allocated landed costs, so once freight allocation exists this must come from the purchase invoice line instead. Correct today; the day it stops being correct is knowable now.
- **`Section.INVENTORY` is new and separate from `PRODUCTS`, because of cost.** Stock *levels* are a product-level read that Remote/Order Staff needs; a *lot* carries its unit cost, which is exactly what `PRODUCT_LAST_PURCHASE_PRICE` keeps from that role. No grants seeded — default-deny.
- **Not built in step 6, all since delivered:** the lot's source-document reference and FIFO consumption both landed in **step 8** (ADR 0004, ADR 0008), and the **write-off table in step 7** once there was a ledger for it to post to. Still absent by decision: **no valuation column** — a lot's value is its remaining quantity extended at its unit cost.

**Bundles — built (step 6), Q11 answered "build now", to brief §5 in full.**

- A bundle is a **Product** with its own SKU and a component list, so a scan, a price tag, a Woo listing and an invoice line can all treat it as one sellable thing.
- **No stock of its own.** It cannot receive a lot, and a product that already has lots cannot become one — either way the same goods would be counted twice. `stockOf` on a bundle computes how many could be assembled per location, limited by whichever component runs out first, by **integer** division: half a component is not half a bundle.
- **`BundleAllocation` is exact integer arithmetic in cents**, largest-remainder, with ties broken by position so the answer is reproducible. Consequently it **never needs a rounding mode and never produces a rounding difference** — `Rounding differences` is for reconciling against an *external* document, not for absorbing our own arithmetic.
- **`BundleDecomposition` enforces in its constructor that the component lines sum to the bundle line.** That is what makes brief §5's "linked, not duplicated" a property of the data: either level gives the same revenue, and adding them together is visibly double-counting. The phase 8 *report* is still phase 8's.
- **Components are one level deep** — a component may not itself be a bundle. Same rule and reasoning as `VatClass`'s island-reduced counterpart: cycles become impossible by construction and allocation stays single-pass.
- **`define` replaces the whole component list, never merges**, so a bundle is never left half-changed and never exists empty (flag and components are set in one transaction).
- **A bundle or a component may be GOODS or SERVICE.** A machine sold with its installation is real; the installation takes allocated revenue and nothing off a shelf, so only *stocked* components constrain availability, and a bundle with no stocked components refuses to report stock rather than answering zero.
- **An unpriced component refuses decomposition** rather than weighing zero — that would push all the revenue onto the priced components and report the unpriced one as pure margin. Same stance as having no fallback VAT rate; `bundlesWithUnpricedComponents()` surfaces it before a sale.
- **Deactivating a component an active bundle needs is refused**, naming the bundles — the same stance as a unit of measure a product still uses.
- **⚠️ Step 9 obligation:** dissolving a bundle that has been sold would strand decomposed component lines; brief §5's "alias forward, never rewrite history" is the shape of the answer and it needs the ledger.

**Journal entries — built (step 7). Q13, Q14, Q19, Q26, Q15 and Q16 all answered.**

- **Two-layer** as the brief has it: typed transactions produce raw balanced entries. Step 7 built the lower layer plus the one typed transaction that *is* a raw entry, the Manual Journal Entry. The other seven arrive in steps 8 and 9.
- **Debits equal credits is a `DEFERRABLE INITIALLY DEFERRED` constraint trigger**, checked at commit, so `CLAUDE.md` rule 6's "structurally" holds against a `psql` session too. Deferral is load-bearing — an entry is legitimately unbalanced between its first line and its last. **Two triggers**, because a trigger on the lines never fires for an entry with *no* lines, which would otherwise be storable. Stored total columns with a single-row CHECK were rejected as a second copy of what the lines say.
- **A named side plus a strictly positive amount, never signed.** Zero is refused as firmly as negative: a zero line balances while stating nothing.
- **Sub-ledger reference required on Control-kind lines** and matched against the account's declared type; **the referenced row is checked to exist by trigger**, using dynamic SQL, because the reference is polymorphic and cannot be a foreign key — and doing it in Java would make the ledger depend on the inventory service, which already depends on the ledger. Permitted on non-Control accounts, which COGS genuinely uses.
- **No balance is stored anywhere.** `balanceOf`, `subLedgerBalanceOf`, `linesOf`, `linesFor` and `trialBalance` all sum on read. A balance on the *wrong* side reads negative rather than being made positive — an overdraft and an overpaid supplier are real and an absolute value would hide them.
- **Q13 (ADR 0006):** immutable documents, editable own-records, nothing ever deleted, reversals verified to be exact mirrors, an entry reversible at most once. A reversal is posted through the ordinary path with `reversalOfEntryId` set, which is what lets a service that owns state outside the ledger reverse its own document without a second unguarded write path.
- **Q14 (ADR 0007):** Output/Input VAT split (V14 repurposed the single `VAT payable`, safe only because nothing had posted yet), VAT class and taxable base on the line, `vatTotals()` to read them back so the columns have a consumer.
- **Q19:** all six typed transactions are Phase 1. **Q26:** a credit note is its own transaction type, immutable like the invoice it corrects. **Q15:** rounding compared **per document**, as the brief says. **Q16:** unallocated credit is a **standalone credit document**, not a bare AR balance. The last three were decisions with nothing built; **all three are built in step 9.**
- **Deliberately absent, as revisited in step 8:** `GOODS_RECEIPT` now exists as a source (Q39 answered); **`source_id` was decided against** rather than added — the document holds the link, one direction. Still absent: a human-facing entry number (Q40), period locking, and any HTTP route.

**Inventory write-off — built (step 7), discharging the step 3 and step 6 obligation.** `stock_write_off` carries `WriteOffReason`, reduces the lot or the named unit **and posts, in one transaction** — either alone is worse than neither. Brief §5's serialized exception is honoured **by construction**, since a write-off always names its lot and nothing picks one for the caller. **A lot carried at zero cost posts no entry and the stock still leaves**: a free sample derecognises nothing, and the ledger rightly refuses a zero-amount line. Reversal restores the quantity or the unit status and posts the mirror together, which is why `JournalService.reverse` refuses this source outright and names `InventoryService.reverseWriteOff` instead.

**Purchasing — built (step 8). ADR 0004's open item, Q17 and Q39 all answered as ADR 0008.**

- **Two documents, either order.** A **Purchase Invoice** is recorded, never issued: it carries the supplier's own number (unique per supplier among documents that stand), is immutable (Q13), and its inventory lines debit **GR/IR clearing** rather than Inventory. A **Goods Receipt** is the inventory event: one lot per line, debit Inventory once per lot, credit GR/IR against the supplier. `InventoryService.receive` is the lower layer it calls and posts nothing on its own.
- **Matching happens when the second document is created**, and there is deliberately no later matching operation — it would need a journal entry belonging to no document, and an unmatched GR/IR balance is exactly what ADR 0004 says it is. Both halves are queryable (`linesAwaitingDelivery` / `linesAwaitingInvoice`) for phase 8's Clearing Checks. `gr_ir_match` is a table, not a foreign key either way, because partial delivery makes it genuinely many-to-many; **it carries no money**, since the variance is stored per invoice line as the residual that makes the line's debits sum to what was charged.
- **The variance can only arise goods-first.** A receipt matched to an existing invoice line takes its cost *from* that invoice and is refused if it restates one — so invoice-first clears exactly and produces nothing to vary.
- **An accepted residual:** one receipt line matched by two invoices can leave a cent in GR/IR. Deliberate — GR/IR is `expected_to_clear` and `ledger.rounding.threshold` already exists to say what is noise.
- **Expense lines exist; automatic categorisation does not.** A line names its account. Brief §7's suggest-from-product-then-supplier-then-`Unclassified` rule is about *choosing* a destination for an invoice nobody typed, and belongs with the myDATA import. **Nothing lands in `Unclassified — Needs Review` by accident.**
- **Every line states either a VAT class or an exemption reason**, never both and never neither. **Reverse charge is a flag that must agree with the supplier's `VatStatus`** — required for `INTRA_EU_B2B`, refused otherwise, never inferred.
- **`source_id` on `journal_entry` was decided against**, discharging the step 7 obligation by answering it: an immutable entry cannot be updated after posting, and storing the link both ways is two copies of one fact. The link lives on the document, one direction, as V15 does for reversals.
- **`SerializedUnitStatus.UNRECEIVED` is new**, for reversing a delivery of machines — and it is the one status that **does not hold its serial number**, since the commonest reason to reverse a delivery is that it was entered wrong.

**FIFO consumption — built (step 8), Q17 answered.** `InventoryService.consume` reduces lots in `lotsOf`'s order (acquisition date, then id), restricted to sellable locations, and posts **one line per lot** (debit COGS, credit Inventory, both carrying the lot reference) in the same transaction. **Pooled stock only** — a serial-tracked product is refused, naming step 9, because selling a named unit means marking it `SOLD` and brief §5 wants the customer and invoice on it. **A shortage does not block**: the unfilled part is recorded, `stockOf` subtracts outstanding shortfalls so the product reads **negative**, and `consumptionsWithShortfall()` is what a review reads. **No COGS is posted for the shortfall** and a later receipt does not retro-cost it; the correction is to reverse and consume again.

**Sales, credit notes and settlements — built (step 9). Q10, Q15's remainder, Q16 and Q26 answered; Q31 confirmed.**

- **The Sales Invoice is recorded, not issued** — Go is the invoicing system of record until phase 11, so `document_number` is Go's and `stated_total` is what Go's document says. Immutable (Q13). **A sale posts two entries**: revenue here, cost of goods sold from `InventoryService`, linked by the consumption the line points at.
- **`SalesChannel` picks the revenue account** — the only place channel exists in the model, which is why step 3 split Sales and Sales returns three ways. A `SERVICE` product credits `Services` instead.
- **`SettlementMethod` picks the debit account** (brief §6): Cash, Card/POS, Skroutz, ACS COD, PayPal and Stripe debit their own account and the invoice is **born fully settled**; `BANK_DEPOSIT` and `ON_ACCOUNT` debit AR and it is an open item. **Bank deposit deliberately does not settle on entry** — a customer saying they transferred is not the money arriving; the Bank Aggregator (phase 6) confirms it. **Cash is hard-blocked at €500** (N. 5301/2026): the one refusal in this design that offers no confirmation, because the confirmation nobody can give is legality.
- **The VAT dimension is supplied** (the step 7 obligation): every Output VAT line carries its class and taxable base, per line summed by class. **`vat_class_source` is stored**, so "why is this line at 13%?" stays answerable after the customer's override has changed.
- **Bundle decomposition is materialised on the invoice**, which is what makes dissolving a sold bundle safe rather than refused — brief §5's "alias forward, never rewrite history" with no alias table, because there is no history to rewrite. ⚠️ **A dual-level revenue report must read the stored components, never `componentsOf`.**
- **Serialized selling** (the step 6 obligation): the line names its machines, each costed at its own lot cost with **no FIFO** (brief §5), marked `SOLD`, carrying the buyer and the invoice line — biconditional by CHECK. **No shortfall on this path**: a named machine is refused rather than flagged, because there is no aggregate for it to be negative in.
- **The Credit Note (Q26)** is its own transaction type: it references the invoice it corrects and each line the invoice line it credits, debits the channel's `Sales returns`, **always credits AR even against a cash sale**, is immutable once issued, and **credits the VAT the sale actually charged** rather than re-resolving the rate.
- **A stock return is not a reversal.** Reversal says the consumption should not have happened (whole quantity, once, exact mirror); a return says the goods came back (partial, repeatable, ordinary entry), at **the cost the stock left at**. A credit note that restored stock is **not reversible** — ADR 0008's principle in the other direction.
- **Receipt and Payment share one table.** `SettlementDirection` decides the side and the `JournalSource`; `PartyType` decides the control account. All four combinations are real, refunds included. The trigger to split them is the first column belonging to one and not the other; there is none today.
- **Q13's second half:** editing a settlement below its allocated total releases allocations **most-recent-first**, reducing the last one partially, every release audit-logged. `allocation_order` exists because `created_at` cannot say which of several created in one transaction was last.
- **Q16:** an overpayment becomes a standalone `customer_credit` document that **posts nothing** — the money is already in AR. Created **only when the caller says so**, because "overpaid" and "unmatched remittance" are different facts (rule 7); the unmatched case stays queryable.
- **Q15's remainder:** a rounding difference above `ledger.rounding.threshold` **refuses the document** until somebody accepts it; at or below it, it posts automatically. **The difference always posts**, so AR agrees with the document the customer holds. The acceptance is stored on the record. **No review queue** — a queue is a second copy of state that goes stale. Generalised: visible-at-entry is confirmed at entry; a consequence the operator cannot fix (Q17's shortfall) is flagged and queried.
- **Q10:** "Πελάτης Λιανικής" is seeded with `CustomerSystemKey.RETAIL_WALK_IN` — VAT treatment fixed at `DOMESTIC` by CHECK, undeactivatable by CHECK, refused on both sides of a merge (merge still not built). **Not a default**; nothing falls back to it.
- **The Bank Transfer** is two lines and no third account — brief §4 drops Manager's Inter Account Transfers, which Manager had under Equity.
- **13 new `AccountSystemKey` values** (3 Sales, 3 Sales returns, `Services`, and the six accounts `SettlementMethod` resolves). No key for `Cost of service sold`, because nothing computes a service's cost.

**Payment settlement automation (brief §6, as built):** Cash→Cash account (hard-blocked >€500, Greek law); POS/Skroutz/ACS→their clearing account (open until real bank remittance); Bank deposit→stays open until Bank Aggregator confirms (chosen: best practice over convenience); Credit→stays open against AR. Real-time balances via frequent (not nightly) Bank Aggregator polling.

**Invoice categorization:** 4 categories (Inventory, Fixed Asset, Expense, Prepaid/Deferred). Freight allocates into inventory lines (proportional by value — known approximation vs. weight-based, accepted). Defaults suggested at Product-level then Supplier-level, else lands in "Unclassified — Needs Review."

**AADE-first invoice import:** default rule — pull from myDATA automatically, confirm against Goods Receipt; missing-from-myDATA is itself a supplier compliance flag.

**Permissions and authentication — built (step 4).**

- **Roles are data, what they grant is code.** `Section` and `ProtectedField` are enums (what exists is determined by what was built); `app_role` / `role_section_grant` / `role_field_restriction` are tables, so creating a role is an operation not a migration — brief §7's "multiple custom roles from the start".
- **Access is default-deny**, so "everything else is invisible" needs no enumeration and stays true as sections are added. **`JOURNAL` is new in step 7** and separate from `CHART_OF_ACCOUNTS` for the reason `INVENTORY` is separate from `PRODUCTS`: seeing the *list* of accounts is close to harmless, while seeing what has posted to them is every financial figure in the business. No grants seeded.
- **Owner and Admin use a `full_access` flag, not stored grants**, so a section added later is visible to them at once. Both are **system roles**: unmodifiable, undeletable, so nobody can strip `USERS_AND_ROLES` from the last role holding it.
- **Remote/Order Staff seeded exactly as answered:** FULL on Sales Order Fulfillment / Customers / Back-in-Stock; VIEW on Products; `PRODUCT_LAST_PURCHASE_PRICE`, `PRODUCT_SUPPLIER`, `PRODUCT_SUPPLIER_SKU` hidden; nothing else. Not a system role, so it stays adjustable. **Field restrictions narrow, never widen.**
- ~~**Step 5 obligation**~~ — **done.** `ProductView.redactedFor(RoleView)` applies all three, tested against the seeded role and, as pure logic, against a last purchase price that cannot exist in real data until step 6.
- **Auth: server-side sessions, HttpOnly cookie** (Q22, approved). `SameSite=Strict`, `Secure`, 8h, new session id on login, CSRF on. Login/logout return 204/401 not redirects, and `/api/**` returns 401 not a redirect — a `fetch()` cannot use a 302 to an HTML login page. No login controller was written; Spring Security's own `/login` and `/logout` are used.
- **Password hashes never leave the core.** `UserService.authenticate(username, rawPassword)` verifies internally; a custom `AuthenticationProvider` in `app` calls it, and the session principal's `getPassword()` returns null. Login failures are indistinguishable (unknown user, wrong password, inactive user, inactive role) with the reason recorded only in the audit log.
- **No seeded account, no default password.** The first Owner comes from `NOVOCORE_BOOTSTRAP_OWNER_USERNAME`/`_PASSWORD` and **the app refuses to start** if the user table is empty and they are unset.
- **Password policy settled (Q29):** 12 characters minimum, no composition rules, per NIST SP 800-63B. **2FA decided as no-for-now with a condition (Q30) — now pre-launch blocker PLB-1, above.** ~~**Q31**~~ **is confirmed in step 9: single role per user stays, no change needed.** Still open: the 8-hour session timeout (Q32).

**REST surface — still one endpoint (step 4b); steps 7, 8 and 9 added none, so the ledger, inventory, purchasing, sales and settlements all have no HTTP route at all.** `GET /api/chart-of-accounts`, read-only. Built specifically to make the `..core.web..` ArchUnit rule load-bearing; its `allowEmptyShould` allowance is removed and the rule was proven to fail against a probe. Authorisation is an explicit typed `requireView(Section...)` call, not a `@PreAuthorize` string that could be misspelled and fail open. **Broader API buildout is deliberately not started.** Note `CoreTestApplication` excludes `..core.web..` from scanning, because the controller needs a `CurrentUser` only `app` implements — a permissive fallback bean in the core was rejected as the thing that later fails open.

**Barcode scanning:** not a module — an input mechanism across Purchase Invoice/Goods Receipt verification, picking, in-store sales, and a new barcode-first entry point into Product Creator (falls back to supplier link, then manual). Once Product Creator exists, NovoCore becomes the point of product creation, syncing outward to Go/Woo — not the reverse.
